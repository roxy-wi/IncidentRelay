# Measured local capacity baseline — 2026-11-09

The current Python implementation handled **20 new alert events/sec for one
minute**, with every event persisted and p95 HTTP latency of **197 ms**. At
40–60 offered events/sec, the corrected load generator encountered significant
queueing and exceeded its bounded in-flight capacity. Exploratory saturation
measurements were approximately 25–40 new events/sec, depending on resources
and client behavior. This is a local baseline, not a universal Python limit or
a production capacity certification.

## Environment and scope

- Source: `29e7f82de1a3a97ef812615b0c3dfd822da81154`; no application source changes.
- Apple M5 host, 10 cores, 24 GiB RAM; Docker VM allocated 4 CPUs and about 5.85 GiB.
- Python 3.12.16, Gunicorn 26.2.0, PostgreSQL 16.15, Linux ARM64 containers.
- Final intake configuration: 4 Gunicorn workers × 4 threads; web limited to
  2 CPUs / 1.5 GiB; PostgreSQL limited to 2 CPUs / 1 GiB.
- Existing deployments remained running. In particular, the existing Telegram
  worker repeatedly used approximately one CPU, competing with this benchmark
  inside the four-CPU Docker VM. CPU allocations were limits, not dedicated cores.
- PostgreSQL data/WAL were on tmpfs, with fsync enabled. Durable-disk performance
  was not measured. Database state grew across stages, ending around 255 MiB.
- One generic webhook event per HTTP request, real route-token authentication,
  distinct alert/group per host, normal full explain tracing unless stated.
- No rotations, service dependency graphs, orchestration rules, or external
  notification providers in the intake fixture; scheduler not running during
  intake. This does not establish capacity for every IncidentRelay feature.

## Final fixed-arrival-rate intake results

Every dispatched request in these final runs returned a validated HTTP 200
completed result. Persisted Alert rows and distinct AlertGroups independently
matched successful response counts. No automatic request retries were used.

| Offered events/sec | Duration | Events offered | Persisted | Client not dispatched | Successful events/sec including drain | HTTP p95 | HTTP p99 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 20 | 30 s | 600 | 600 | 0 | 19.42 | 75 ms | 1,199 ms |
| 20 | 60 s | 1,200 | 1,200 | 0 | 20.00 | 197 ms | 674 ms |
| 40 | 30 s | 1,200 | 1,053 | 147 (12.3%) | 33.75 | 5,018 ms | 5,828 ms |
| 60 | 30 s | 1,800 | 1,254 | 546 (30.3%) | 39.38 | 4,021 ms | 4,172 ms |
| 60, trace disabled | 30 s | 1,800 | 1,354 | 446 (24.8%) | 42.88 | 3,630 ms | 3,924 ms |

The client allowed at most 64 requests in flight. **Client not dispatched means
the generator's bound was reached; it is not an HTTP rejection or a server-side
drop.** A producer that continued sending without that bound would accumulate
more outstanding work. Percentiles describe dispatched requests only; the
missing offered arrivals must be considered separately. Throughput includes
time spent draining the final requests.

These runs show comfortable baseline throughput at 20/sec and an unreliable
latency/queueing region at 40–60/sec in this environment. They do not locate an
exact threshold between 20 and 40. Tail pauses and variation between runs matter.
For example, an earlier keep-alive 40/sec run completed all 2,400 events over a
minute with p95 354 ms; the fresh-connection run above did materially worse.
Client behavior, state growth, background load, and resource contention prevent
claiming a single precise hardware-independent maximum.

Disabling trace storage increased observed overloaded throughput from 39.38 to
42.88/sec in these probes, about 9%, but did not sustain the offered 60/sec rate.
This is a configuration tradeoff with lost diagnostics, not a recommendation to
disable tracing universally or a controlled estimate of its isolated cost.

## Worker/resource exploration

The earlier closed-loop matrix used persistent HTTP connections and 15–20 second
stages. Clients waited for responses before issuing another event, so these
measure saturation rather than fixed-arrival-rate reliability.

| Workload/configuration | Successful events/sec | p95 |
|---|---:|---:|
| New alerts, 1 worker / 1 PG CPU, concurrency 1 | 19.98 | 57 ms |
| New alerts, 1 worker / 1 PG CPU, concurrency 16 | 29.12 | 618 ms |
| New alerts, 4 workers / 1 PG CPU, concurrency 16 | 29.06 | 882 ms |
| New alerts, 4 workers / 2 PG CPUs, concurrency 16 | 38.15 | 567 ms |
| Repeated alerts across 100 identities, 4 workers / 2 PG CPUs | 44.25 | 538 ms |
| Repeated events on one identity, 4 workers / 1 PG CPU | 32.00 | 843 ms |

At one PG CPU, samples approached its CPU quota and cgroup statistics showed
throttling. Increasing Gunicorn workers alone did not improve throughput.
Sampled web memory rose from roughly 108 MiB with one worker to roughly
360–372 MiB with four. PostgreSQL memory includes the tmpfs data/WAL and therefore
must not be interpreted as database-process RSS.

## Separate notification-delivery limits

The real `alert_group_notification_job()` sent 100 groups through a real HTTP
webhook notifier to a controlled localhost server. All three batches reported
100 sent, zero skipped/failed, and 100 independently observed HTTP deliveries.
The job was invoked directly once per probe; periodic scheduling was not running.

| Added provider response delay | 100-group batch duration | Batch service throughput |
|---:|---:|---:|
| 0 ms | 1.130 s | 88.48 groups/sec |
| 100 ms | 11.610 s | 8.61 groups/sec |
| 500 ms | 51.675 s | 1.94 groups/sec |

Delivery iterates groups sequentially. The default job takes at most 100 groups
per 10-second scheduler tick, with one instance and a job-wide database lock.
Consequently, its cadence caps processing at **10 groups/sec**, even with an
instant provider. With slow providers, the batch takes longer than a tick and
the actual periodic throughput is lower than the batch service rates above.
Multiple channels per group, failures, and retry traffic can reduce it further.
These are group-delivery limits, not raw inbound-event limits: deduplication and
grouping change how many events require notifications.

The default initial group wait is **30 seconds**, before scheduler delay and
delivery time. This is configured batching behavior, not an intake benchmark
result. The delivery probes deliberately set groups due immediately.

Source pointers:

- `app/settings.py:418`: initial wait, check cadence, batch size defaults.
- `app/services/scheduler.py:216`: batch job and distributed lock.
- `app/services/scheduler.py:820`: interval, `max_instances=1`, coalescing.
- `app/services/alerts/notification_queue.py:339`: sequential delivery loop.

## Concrete overhead found

Profiling 20 new alerts through Flask's test client counted, per event:

| SQL operation | Statements/event |
|---|---:|
| SELECT | 43 |
| INSERT | 24 |
| UPDATE | 10 |
| SAVEPOINT / RELEASE combined | 4 |
| **Total instrumented application SQL calls** | **81** |

This includes full explain tracing, which persists explain steps individually.
Driver connection/transaction setup adds work outside that instrumentation.
The application also opens/closes a database connection per request using a
non-pooled Peewee database. SQL count, trace writes, query construction, and
connection lifecycle are concrete optimization candidates. The profiler itself
adds overhead, so its wall time is not used as an HTTP capacity measurement.

The idle Telegram loop is another concrete issue. In an isolated database with
zero Telegram channels, calling the actual poller exactly as the worker does
completed **6,264 iterations/SQL queries in 3 seconds**: **2,088 queries/sec**, with
1.95 seconds of Python CPU time and no useful work. `app/telegram_worker.py`
sleeps after exceptions but has no wait after an immediate successful empty
poll. The existing container's roughly 100% CPU use is consistent with this
path, although its precise live internal state was not inspected.

## Evidence, reproduction, and boundaries

See [README.md](README.md) for runnable commands and fixture details. Raw records,
runtime/image metadata, available CPU/memory samples, SQL profile, and delivery
results are saved under [results/2026-11-09](results/2026-11-09).

Final intake rows have `transport: connection-close`. Earlier rows are retained
as exploratory evidence. One early minute-long keep-alive run had 11 broken-pipe
client errors from reusing expired sockets; it is excluded from final capacity
claims. The client was corrected and the 20/sec minute-long run repeated cleanly.

Validation: real PostgreSQL HTTP probes with persisted-row checks; 300 observed
local HTTP deliveries; Python compilation; Ruff 0.16.0 bug-oriented checks;
Compose configuration validation. The full application regression suite was
not run because application behavior was not changed. No production capacity,
live provider throughput, large-history performance, or Go performance is
established by these tests.

The first improvements justified by this evidence are idle-worker backoff,
reducing/batching SQL work, and bounded parallel delivery with durable claims.
The measurements do not establish that a language rewrite is necessary.
