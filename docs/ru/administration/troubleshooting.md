# Устранение неполадок

## 500 при дублирующихся именах или slug'ах

Дублирующиеся ресурсы должны возвращать `409 Conflict`, а не `500`. Проверьте логи API на наличие `IntegrityError` и добавьте явную обработку ошибок в соответствующем представлении.

Типовые примеры:

- дублирующийся slug группы;
- дублирующийся slug команды;
- дублирующийся slug сервиса внутри одной команды;
- дублирующееся имя канала внутри одной команды.

## Пустое тело возвращает непонятную ошибку валидации

Эндпоинты POST/PUT должны возвращать структурированную `400 validation_error`, когда тело отсутствует или содержит некорректный JSON.

## Некорректная дата в календаре возвращает 500

Параметры запроса, такие как `start` и `end`, должны валидироваться до того, как разбор даты дойдёт до бизнес-логики.

## Тест email работает, а реальный алерт — нет

Проверьте:

1. У реального алерта есть ответственный.
2. У назначенного пользователя указан email в профиле.
3. Канал привязан к сопоставленному маршруту.
4. Фильтр серьёзности пропускает серьёзность алерта.
5. SMTP-релей принял и доставил сообщение.

## Голосовой вызов не проходит из-за отсутствующего телефона

Голосовой вызов отправляется на номер телефона из профиля назначенного пользователя. Укажите `phone` у назначенного пользователя.

## Ошибка токена Telegram

Токен бота Telegram должен содержать двоеточие:

```text
123456789:AA...
```

Если токен недействителен, исправьте конфигурацию канала или отключите канал.

## Напоминания дублируются

Проверьте, что запущен только один процесс планировщика и что планировщик не запускается внутри каждого веб-воркера.

## Алерт не виден

Проверьте:

1. Использован правильный токен приёма маршрута (route intake token).
2. Эндпоинт соответствует источнику маршрута.
3. Матчеры маршрута сопоставляются с метками алерта.
4. Группа активна.
5. Команда активна.
6. Активная группа в UI выбрана правильно.
7. Выбрано `All my groups`, когда алерт может принадлежать другой доступной группе.
8. `routing_error` в ответе интеграции.
9. JSON-логи по `error_id`, если сервер его вернул.

## У алерта нет сервиса

Если алерт создан, но сервис пуст:

1. Проверьте, что у маршрута есть сервис по умолчанию.
2. Проверьте, что существует правило сопоставления сервиса.
3. Проверьте, что правило сопоставления сервиса включено.
4. Проверьте, что правило ограничено правильным маршрутом или не имеет ограничения по маршруту.
5. Проверьте, что метки, аннотации или поля payload соответствуют правилу.
6. Проверьте, что сервис и владеющая им команда включены.

Пример правила сопоставления сервиса Alertmanager:

```json
{
  "labels": {
    "job": "RabbitMQ",
    "rabbitmq": {
      "op": "regex",
      "value": "^rabbitmq-cloud$"
    }
  }
}
```

## Ссылки сервиса или runbook'и не отображаются в уведомлениях

Проверьте:

1. У алерта есть `service_id`.
2. Ссылка сервиса или runbook включены.
3. Ссылка сервиса или runbook не удалены.
4. Матчеры runbook'а пусты либо соответствуют меткам/аннотациям/payload алерта.
5. Форматтер уведомлений поддерживает контекст сервиса для выбранного канала.

Поведение матчеров runbook'а:

```text
empty matchers -> generic runbook for all alerts of the service
matchers set -> only matching alerts
```

## Браузерные push-уведомления отключены или не настроен публичный ключ VAPID

Проверьте эндпоинт конфигурации профиля:

```text
GET /api/profile/push/vapid-public-key
```

Ожидаемый ответ:

```json
{
  "enabled": true,
  "public_key": "B..."
}
```

Если `enabled` равно false или `public_key` равно null, исправьте конфигурацию `[browser_push]` и перезапустите веб-сервис. Перезапустите также планировщик, если он отправляет уведомления в вашей установке.

## Тест браузерного push работает, а реальный алерт — нет

Тестовый push отправляется текущему пользователю профиля. Push реального алерта отправляется на `alert.assignee_id`.

Проверьте:

1. У алерта есть ответственный.
2. Ответственный — тот же пользователь, который включил push в профиле.
3. У строки подписки `enabled = true` и `deleted = false`.
4. Браузерные push-уведомления включены в конфигурации.
5. `/service-worker.js` актуален в браузере пользователя.

Браузерные push-уведомления не являются каналом, поэтому они не отображаются в привязках каналов маршрута.

## Действие браузерного push возвращает token_expired

Одноразовый токен ACK/Resolve был старше `[browser_push] action_token_ttl_seconds`, когда браузер отправил действие.

## Действие браузерного push возвращает token_already_used

Тот же токен действия уведомления уже был использован. Это может произойти после двойного клика, повторной попытки браузера или нажатия на то же действие уведомления более одного раза.

## Имя сервиса, команды или группы отображается как `-`

Код отображения должен использовать такой порядок:

```text
name -> slug -> "-"
```

Для ссылок и runbook'ов убедитесь, что сериализаторы включают:

```text
service_id
service_name
service_slug
team_id
team_name
team_slug
```
