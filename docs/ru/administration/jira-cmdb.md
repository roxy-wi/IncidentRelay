# Синхронизация Jira CMDB

В разделе **Администрирование → Синхронизация** доступен тип **Сервисы и бизнес-сервисы · Jira CMDB** для Jira Data Center / Server. IR читает данные из Jira. Нужны права глобального администратора или администратора целевой группы и запущенный планировщик IR.

## Настройка и импорт

1. Создайте источник типа Jira CMDB. Укажите группу IR, базовый URL Jira и заголовки авторизации. Заголовки шифруются и не возвращаются в браузер; пустое поле при редактировании сохраняет прежние значения.
2. Укажите путь поиска: обычно `/rest/assets/1.0/aql/objects`, для старых версий Insight — `/rest/insight/1.0/iql/objects`. Выберите поддерживаемый сервером параметр `qlQuery` или `iql`. Проверка TLS, разрешённые сети и ограниченные повторы запросов работают как у синхронизации команд.
3. Задайте отдельные AQL-запросы для сервисов и бизнес-сервисов. `objectType = "System"` и `objectType = "Product"` — изменяемые примеры. Можно выбирать другие типы, схемы и условия. Выборки не должны пересекаться. Для постраничной загрузки при необходимости задайте стабильную сортировку в AQL.
4. Сохраните источник и нажмите **Загрузить поля и команды**. Планировщик загрузит данные; интерфейс покажет ход операции. Каталог при этом не меняется.
5. Выберите **поле команды-владельца отдельно для каждой выборки**. Атрибуты выбираются по ID или точному имени. По умолчанию название берётся из метки объекта. Описание, запасное описание, окружение, критичность и статус жизненного цикла необязательны. После смены поля владельца сохраните настройки и повторно загрузите команды.
6. Выберите активную команду IR в целевой группе для каждой команды CMDB или включите **Создавать отсутствующие команды в IR**. Для пустых строк IR подберёт команду по полному имени без учёта регистра и пробелов по краям. Новые команды появятся в предпросмотре и будут созданы при применении. При неоднозначном имени выберите команду вручную. Несколько команд CMDB можно вручную сопоставить с одной командой IR. IR запомнит сопоставления по ID и будет использовать эту настройку при синхронизации по расписанию.
7. Выберите сторону и атрибут связи. Например, `System.Product` включает сервис в состав бизнес-сервиса. Поддерживаются несколько ссылок и обратное направление связи.
8. Для импорта технических зависимостей выберите в разделе **Сервисы** настройку **Поле зависимостей между сервисами**, например `Prod System`. Если у системы A в этом поле указана B, в IR система A зависит от B. Настройка необязательна и действует независимо от поля `Product`.
9. Сохраните настройки, создайте **Превью**, проверьте изменения и нажмите **Применить**. После успешного применения выбранное расписание запускается автоматически.

В разделе **Сопоставление значений окружения и критичности** используются JSON-словари `environment_values`, `criticality_values`, `business_criticality_values`. Для неизвестного значения нужно задать соответствие. Статус жизненного цикла, включая `status.name` из Assets, сохраняется в `metadata.jira_cmdb` и не заменяет состояние работоспособности.

## Обновления и сохранность данных

В превью зависимости обозначены как `dependency`. Поле `service` содержит ID зависимой системы в CMDB, а `depends_on_service` — ID системы, от которой она зависит. Новые зависимости получают тип `hard` и критичность `important`. Ручные зависимости и локальные настройки существующих связей сохраняются. IR удаляет созданную источником зависимость, если обе системы вошли в импорт и ссылка исчезла. Если очистить поле зависимостей в настройках источника, ранее созданные связи сохранятся.

Если A ссылается на B, а в текущую выборку AQL вошла только A, IR ищет B по её CMDB ID среди сервисов, ранее импортированных этим источником. Для создания зависимости подходит включённый сервис в группе назначения. В превью его локальный ID виден в `depends_on_service_ir_id`. Данные самой B сохраняются. Если подходящего сервиса нет или Jira пометила B как архивную, IR пропускает зависимость и показывает предупреждение.

- Объекты определяются по источнику и внешнему ID. Переименование сохраняет объект и его slug.
- При чтении поля владельца IR пропускает команды, для которых Jira Assets вернула `referencedObject.archived: true`. Если в поле есть ещё и действующая команда, IR использует её. Если все команды архивные, применяются правила для пустого поля владельца.
- Если в Jira поле владельца пусто или отсутствует, уже импортированные объекты сохраняют свою команду и получают остальные обновления. Новый бизнес-сервис создаётся без владельца. Новый технический сервис появится в предупреждениях и будет импортирован, когда в Jira укажут команду и её сопоставят в IR. Остальные объекты можно применить сразу.
- Меняются выбранные поля. Локальные политики, каналы, ручной статус, прочие метаданные и вручную созданные связи сохраняются.
- Новые бизнес-сервисы не публикуются. Для несопоставленных полей и новых правил влияния компонентов используются значения IR по умолчанию. Последующие обновления сохраняют локальные настройки влияния компонентов.
- Смена команды сервиса блокируется, пока к нему привязаны ротация, политики или каналы команды. Эти настройки нужно согласовать до переноса.
- Отсутствующие или исключённые фильтром объекты сохраняются. Импортированная связь удаляется только при загрузке обоих объектов и отсутствии ссылки между ними. Для связей с бизнес-сервисами ссылки за пределы выборки показываются как предупреждения.
- Смена запросов, полей и сопоставлений требует нового превью. Изменение интервала пересчитывает следующую проверку от момента сохранения без нового превью.
- После успешного импорта нельзя менять группу назначения и базовый URL Jira.

Все страницы загружаются до записи в каталог. Повторяющиеся ID, неполная загрузка, изменение количества объектов, ошибки HTTP, истёкшая блокировка или устаревшее превью прерывают импорт без потери существующих данных. Ошибки записываются в лог без токенов и сырых ответов Jira; повторы по расписанию используют заданный интервал.

## Удаление и повторное подключение

При удалении источника можно **оставить** или **удалить импортированные сервисы и бизнес-сервисы**. При сохранении новый источник для того же URL Jira и группы IR привяжет объекты по внешним ID после превью. Удаление затрагивает только созданные источником объекты и их зависимые настройки через обычный механизм удаления IR. Команды IR сохраняются, в том числе созданные автоматически.

## API

Используется `/api/admin/directory-sync` с `config.source_type: "jira_assets"`. В `/options` доступен `cmdb_preset`. `POST /{id}/inspect` ставит загрузку полей в очередь с текущей `revision`. Состояние читается через `GET /{id}`: `pending_mode`, `running`, `preview_result.attributes`, `team_catalog`, `issues`, `warnings`. Для применения необходим действующий `preview_token`. Прежние источники и права токенов `directory-sync:read/write` сохраняют совместимость.
