# Алерты и группы алертов

IncidentRelay сохраняет каждый входящий сигнал мониторинга как **алерт** и показывает операторам **группу алертов** на странице Alerts.

Группа алертов — это объект уровня инцидента. Именно этот объект пользователи подтверждают, разрешают, по нему отправляют уведомления, напоминания, эскалации и его объединяют.

Дочерний алерт — это конкретный сигнал внутри группы. Например, три алерта `DiskFull` с трёх хостов могут отображаться как одна группа алертов с тремя дочерними алертами.

## Основные термины

| Термин | Значение |
| --- | --- |
| Группа алертов | Объект уровня инцидента, отображаемый на странице Alerts. |
| Дочерний алерт | Конкретный входящий сигнал внутри группы алертов. |
| `dedup_key` | Идентифицирует один конкретный алерт и используется для обновления того же дочернего алерта. |
| `group_key` | Определяет, какие дочерние алерты относятся к одной и той же группе алертов. |
| `group_by` | Настройка маршрута, управляющая тем, какие поля используются для построения `group_key`. |
| Merge | Ручная операция, перемещающая дочерние алерты из одной группы в другую. |

## Дедупликация против группировки

Дедупликация и группировка решают разные задачи.

`dedup_key` обновляет один и тот же конкретный алерт. Если тот же алерт получен повторно с тем же `dedup_key`, IncidentRelay обновляет существующий дочерний алерт вместо создания нового.

`group_key` объединяет несколько связанных дочерних алертов в одну группу алертов. Если у двух алертов разные значения `dedup_key`, но одинаковый `group_key`, они становятся разными дочерними алертами внутри одной группы алертов.

Пример:

```json
{
  "labels": {
    "alertname": "DiskFull",
    "severity": "critical",
    "instance": "host1"
  },
  "fingerprint": "disk-full-host1-var"
}
```

и:

```json
{
  "labels": {
    "alertname": "DiskFull",
    "severity": "critical",
    "instance": "host2"
  },
  "fingerprint": "disk-full-host2-var"
}
```

С маршрутом `group_by = ["alertname", "severity"]` оба алерта помещаются в одну группу, потому что у них совпадают `alertname=DiskFull` и `severity=critical`.

С маршрутом `group_by = ["alertname", "severity", "instance"]` они помещаются в разные группы, потому что `instance` различается.

## Группировка по умолчанию

Если маршрут не задаёт `group_by`, IncidentRelay использует группировку по умолчанию:

```text
alertname
severity
```

Ключ группы также ограничивается по источнику, команде, маршруту и сервису. Это не позволяет несвязанным маршрутам или сервисам случайно объединиться в одну группу, даже когда метки выглядят похоже.

## Настройка `group_by` маршрута

`group_by` маршрута принимает список имён полей.

Рекомендуемые примеры:

```json
["alertname", "severity"]
```

Группировать по имени алерта и уровню важности. Это полезно для алертов, разлетающихся по хостам, когда множество хостов сообщают об одной и той же проблеме.

```json
["alertname", "severity", "instance"]
```

Группировать по имени алерта, уровню важности и инстансу. Это оставляет каждый хост в отдельной группе.

```json
["alertname", "severity", "mountpoint"]
```

Группировать дисковые алерты по точке монтирования, при этом по-прежнему позволяя объединять несколько инстансов, если это ожидаемо для команды.

Поддерживаемые формы полей:

| Форма | Пример | Значение |
| --- | --- | --- |
| Простое имя метки | `alertname` | Читает сначала из меток, затем из аннотаций, затем из данных алерта верхнего уровня. |
| Явный путь к метке | `labels.instance` | Читает из меток алерта. |
| Явный путь к аннотации | `annotations.summary` | Читает из аннотаций алерта. |
| Явный путь в полезной нагрузке | `payload.trigger.id` | Читает из нормализованной полезной нагрузки. |
| Встроенная область | `source`, `team`, `route`, `service` | Использует метаданные IncidentRelay, полученные при маршрутизации. |

## Жизненный цикл группы алертов

### Firing

Новая группа начинается в состоянии `firing`, когда хотя бы один дочерний алерт находится в состоянии firing.

Если в ту же группу добавляется другой дочерний алерт, счётчики пересчитываются, и группа остаётся в состоянии `firing`.

### Acknowledged

Подтверждение группы алертов помечает группу как `acknowledged`.

Дочерние алерты по отдельности не подтверждаются. Это сделано намеренно: оператор подтверждает группу уровня инцидента, а не каждый исходный сигнал мониторинга.

Если в подтверждённую группу приходит новый дочерний алерт, IncidentRelay обычно снова открывает группу как `firing`. Если маршрут сгруппирован только по `incident_key`, дочерний алерт с тем же непустым значением сохраняет `acknowledged`, если он не может повысить фактический приоритет инцидента. Существенное повышение приоритета всё равно открывает группу повторно: обычные коррелированные сигналы не пейджат дежурного ещё раз, а реальное ухудшение остаётся заметным.

### Resolved

Разрешение группы алертов разрешает все дочерние алерты в группе.

Когда для существующих дочерних алертов приходят входящие полезные нагрузки resolved, группа разрешается только тогда, когда разрешены все дочерние алерты.

Осиротевшая полезная нагрузка resolved не создаёт новую группу.

## Комментарии

Детали алерта включают раздел Comments для заметок ответственных.

Комментарии можно использовать для контекста расследования, заметок при передаче смены, деталей смягчения последствий, ссылок на дашборды или тикеты, а также для последующих действий после разрешения.

Подробнее: [Комментарии к алертам](alert-comments.md).

### Merged

Исходная объединённая группа помечается как `merged` и указывает на целевую группу. Дочерние алерты из исходной группы перемещаются в целевую группу.

Объединённые группы скрыты из обычного списка алертов, если только API/UI явно не запрашивает их включение.

## Уведомления группы

Группы алертов поддерживают отложенные и пакетные уведомления.

Первое уведомление о firing может быть отложено на `ALERT_GROUP_WAIT_SECONDS`. Это даёт IncidentRelay время собрать несколько дочерних алертов в одну группу перед уведомлением пользователей.

Обновления после первого уведомления ограничиваются по частоте параметром `ALERT_GROUP_INTERVAL_SECONDS`.

Если группа разрешается до отправки первого уведомления, IncidentRelay очищает ожидающее уведомление о firing и не отправляет шумные устаревшие уведомления.

Если группа уже была уведомлена, а затем разрешается, IncidentRelay немедленно отправляет уведомление о разрешении.

Соответствующие настройки:

```ini
[alerts]
alert_group_wait_seconds = 30
alert_group_interval_seconds = 300
alert_group_notification_check_interval_seconds = 10
alert_group_notification_batch_size = 100
```

## Ручные инциденты

Ручные инциденты позволяют ответственным и редакторам создать инцидент напрямую из UI или API, когда проблема известна до того, как внешняя система мониторинга отправит алерт.

Ручной инцидент сохраняется как обычная группа алертов с одним дочерним алертом:

- `source` группы алертов — `manual`;
- `source` дочернего алерта — `manual`;
- статус начинается как `firing`;
- подтверждение, разрешение, ответственные, заинтересованные стороны, комментарии, приоритет и хронология работают так же, как для групп алертов, созданных интеграцией.

Ручные инциденты не требуют маршрута приёма. Создатель выбирает команду напрямую и может дополнительно выбрать сервис.

Если сервис выбран, IncidentRelay может использовать принадлежность сервиса, ротацию по умолчанию, политику эскалации и политику уведомлений. Каналы маршрута не используются для ручных инцидентов без маршрута.

### Разрешения

Пользователь может создать ручной инцидент для команды, если он является одним из:

- глобальный администратор;
- редактор группы или администратор группы для группы команды;
- менеджер команды;
- ответственный команды.

Наблюдатели не могут создавать ручные инциденты.

### Пример API

```bash
curl -X POST https://incidentrelay.example.com/api/incidents \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "team_id": 12,
    "service_id": 34,
    "title": "Storage API is unavailable",
    "message": "Customers are receiving 5xx from storage-api.",
    "severity": "critical",
    "priority": "p1",
    "notify": true
  }'
```

Поведение уведомлений

Когда `notify` равно true, IncidentRelay планирует обычное уведомление группы алертов. Для ручных инцидентов без маршрута доставка определяется через политику уведомлений выбранного сервиса.

Если сервис не выбран или у выбранного сервиса нет подходящего правила политики уведомлений, инцидент всё равно создаётся, но цель уведомления может быть не найдена.

## Ручное объединение

Ручное объединение полезно, когда две группы были созданы отдельно, но фактически описывают один инцидент.

UI может объединять выбранные группы алертов. Целью является группа, которая остаётся видимой. Дочерние алерты из других групп перемещаются в целевую группу.

Пример API:

```bash
curl -X POST https://incidentrelay.example.com/api/alerts/merge \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "target_group_id": 101,
    "source_group_ids": [102, 103],
    "reason": "Same customer-facing incident"
  }'
```

Ответ — целевая группа алертов с пересчитанными счётчиками.

## Совместимость API

Путь Alerts API остаётся:

```text
/api/alerts
```

Для совместимости с существующими UI и клиентами элементы ответа по-прежнему возвращаются из `/api/alerts`, но каждый элемент теперь является группой алертов.

Поле `id` в ответах `/api/alerts` — это идентификатор группы алертов.

Детали доступны по адресу:

```text
GET /api/alerts/{alert_id}
```

Имя параметра пути сохранено как `alert_id` для совместимости, но его следует рассматривать как идентификатор группы алертов.

## Примеры API

### Список групп

```bash
curl -H "Authorization: Bearer TOKEN" \
  "https://incidentrelay.example.com/api/alerts?status=firing&severity=critical"
```

### Получить детали группы

```bash
curl -H "Authorization: Bearer TOKEN" \
  "https://incidentrelay.example.com/api/alerts/101"
```

Ответ с деталями содержит:

```json
{
  "type": "alert_group",
  "id": 101,
  "status": "firing",
  "alert_count": 2,
  "firing_count": 2,
  "alerts": [
    {
      "type": "alert",
      "id": 501,
      "status": "firing",
      "dedup_key": "disk-full-host1-var"
    },
    {
      "type": "alert",
      "id": 502,
      "status": "firing",
      "dedup_key": "disk-full-host2-var"
    }
  ]
}
```

### Подтвердить группу

```bash
curl -X POST https://incidentrelay.example.com/api/alerts/101/ack \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

### Разрешить группу

```bash
curl -X POST https://incidentrelay.example.com/api/alerts/101/resolve \
  -H "Authorization: Bearer TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

## Устранение неполадок

### Алерты не группируются

Проверьте значение `group_by` маршрута. Если включена метка `instance`, `pod`, `container` или другая метка с высокой кардинальностью, IncidentRelay может создавать по одной группе на хост или на pod.

### Несвязанные алерты группируются

Добавьте больше полей в `group_by` маршрута, например `instance`, `mountpoint`, `service` или другую метку, разделяющую инциденты для команды.

### Группа была подтверждена, но снова стала firing

Новый дочерний алерт либо пришёл не по маршруту, сгруппированному только по `incident_key`, либо не содержал тот же непустой ключ, либо мог повысить фактический приоритет инцидента. Сигналы, которые не могут повысить фактический приоритет, с совпадающим ключом на таком маршруте сохраняют подтверждение; остальные новые дочерние алерты снова открывают группу, чтобы изменение было заметно.

### Уведомление о разрешении не было отправлено

Если группа разрешилась до отправки первого отложенного уведомления, IncidentRelay намеренно пропускает как уведомление о firing, так и о разрешении, чтобы избежать шума.

### Группа исчезла после объединения

Исходная группа была помечена как `merged`. Откройте целевую группу, чтобы увидеть перемещённые дочерние алерты.
