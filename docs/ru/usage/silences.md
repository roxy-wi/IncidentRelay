# Заглушки

Заглушки (silence) временно подавляют уведомления об алертах для планового обслуживания, шумных алертов или известных инцидентов, не требующих вызова.

Заглушка принадлежит одной команде и использует общий формат матчеров IncidentRelay. Когда входящий алерт совпадает с активной заглушкой, IncidentRelay помечает его как заглушённый и пропускает обычные уведомления.

## Как работает сопоставление

Все условия в объекте матчера заглушки используют семантику **AND**. Пустой объект совпадает с каждым алертом в команде и должен использоваться только намеренно.

```json
{}
```

Сопоставить конкретный алерт на одном инстансе:

```json
{
  "alertname": "DiskFull",
  "instance": "host1.example.com"
}
```

Структурированная форма меток эквивалентна:

```json
{
  "labels": {
    "alertname": "DiskFull",
    "instance": "host1.example.com"
  }
}
```

См. [Матчеры алертов](../concepts/matchers.md) для полного описания общего формата, операторов значений и поведения редактора матчеров.

## Примеры матчеров

### Заглушить предупреждающие алерты CPU

```json
{
  "alertname": "HighCPU",
  "severity": "warning"
}
```

### Заглушить критические алерты для сервиса

```json
{
  "service": "billing-api",
  "severity": "critical"
}
```

### Заглушить группу хостов по регулярному выражению

```json
{
  "instance": {
    "regex": "^web-[0-9]+\\.example\\.com$"
  }
}
```

### Заглушить алерты Kubernetes по namespace

```json
{
  "namespace": "staging"
}
```

### Исключить одно значение

```json
{
  "environment": {
    "not": "production"
  }
}
```

### Совпадение с одним из нескольких значений

```json
{
  "severity": ["warning", "info"]
}
```

## Подсказки матчеров

Общий редактор матчеров может загружать известные имена меток и наблюдаемые значения из недавних алертов в выбранной команде.

Подсказки помогают избежать орфографических ошибок, но они не сохраняют заглушку и не гарантируют, что будущие алерты будут использовать те же метки. Проверьте сгенерированный JSON перед сохранением.

## Статусы

| Статус | Значение |
|---|---|
| Active | Заглушка включена, и текущее время находится между `starts_at` и `ends_at`. |
| Scheduled | Заглушка включена, но `starts_at` в будущем. |
| Expired | Заглушка завершилась. Истёкшие заглушки по умолчанию скрываются после окна хранения. |
| Disabled | Заглушка была отключена вручную и остаётся видимой для просмотра. |

## История истёкших заглушек

Истёкшие заглушки скрываются, когда они старше настроенного окна хранения. По умолчанию истёкшие заглушки исчезают из обычного списка через 30 дней после `ends_at`.

Включите историю истёкших заглушек на странице Silences, чтобы найти более старые записи для аудитов и устранения неполадок.

## Отключённые заглушки

Отключение заглушки не удаляет её. Отключённая заглушка остаётся видимой, чтобы пользователи могли понять, почему она больше не применяется.

Используйте отключённые заглушки для просмотра и истории аудита. Используйте истёкшие заглушки для жизненного цикла, основанного на времени.

## Рекомендуемая стратегия матчеров

Держите заглушки настолько узкими, насколько это возможно.

Предпочтительно:

```json
{
  "alertname": "DiskFull",
  "instance": "host1.example.com"
}
```

Избегайте широких матчеров, если только окно обслуживания не является намеренным:

```json
{
  "severity": "critical"
}
```

Широкая заглушка может подавить несвязанные инциденты.

## Распространённые метки

Точный набор меток зависит от полезной нагрузки входящей интеграции.

| Метка | Пример |
|---|---|
| `alertname` | `DiskFull` |
| `severity` | `critical` |
| `instance` | `host1.example.com` |
| `job` | `node-exporter` |
| `service` | `billing-api` |
| `namespace` | `production` |
| `cluster` | `prod-eu-1` |

Матчеры Alertmanager обычно нацелены на значения из `alerts[].labels`. Для полезных нагрузок Zabbix или обобщённых вебхуков используйте метки, сохранённые в итоговом алерте.

## Устранение неполадок

Если заглушка не совпадает с алертом:

1. Проверьте метки алерта на странице деталей алерта.
2. Убедитесь, что каждое имя матчера существует в сохранённых метках алерта или нормализованном контексте.
3. Убедитесь, что точные значения используют то же написание и регистр.
4. Проверьте регулярные выражения на фактически сохранённом значении.
5. Убедитесь, что заглушка активна, включена и принадлежит той же команде, что и алерт.
6. Убедитесь, что алерт был получен, пока заглушка была активна.

Если заглушается слишком много алертов, добавьте метки, такие как `alertname`, `instance`, `service`, `namespace` или `severity`, чтобы сузить матчер.
