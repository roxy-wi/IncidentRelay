# Stakeholders Incident

Stakeholder следит за операционным Incident. Подписка не делает его responder и
не выдаёт доступ к Incident. Адресат — активный пользователь или внешний email.
При создании Incident с основным сервисом его активные владельцы копируются в
независимый снимок подписчиков.

## API

```http
POST /api/incidents/17/stakeholders
Content-Type: application/json

{"email":"support@example.com","display_name":"Поддержка","role":"observer"}
```

Укажите ровно один непустой `email` или ненулевой `user_id`. Email очищается от
пробелов по краям и приводится к нижнему регистру. Email и имя ограничены 255
символами. Роли ручного добавления: `stakeholder` (по умолчанию), `communications`,
`observer`. Унаследованные роли владельцев и legacy-записей сохраняются в ответах.
Внутренний пользователь должен состоять в группе Incident.

- `GET /api/incidents/17/stakeholders` возвращает активных подписчиков.
- POST возвращает `201` при создании или повторной активации; существующий активный
  адресат возвращается без изменений с `200`. Повторный POST не обновляет его поля.
- `DELETE /api/incidents/17/stakeholders/<id>` деактивирует подписку (`204`), сохраняя
  историю. Повторное удаление возвращает `404`.

Чтение требует доступа к команде, запись — права реагирования и пользователя.
API Incident не принимает notification flags и не предоставляет endpoint их
редактирования. Флаги копируются из [настроек сервиса](../services/default-stakeholders.md).

## Доставка и повторы

Флаги снимка управляют уведомлениями о создании, изменении приоритета/workflow,
операционном resolve и комментариях Incident. Автор не получает своё stakeholder
уведомление. Технические ACK/resolve и комментарии AlertGroup не заменяют эти события.

Получатели и содержимое доставки сохраняются в одной транзакции с событием.
Email и browser push независимы. Внешний адресат получает только email; push
требует активного пользователя и пригодных подписок браузера. Stakeholder push
информационный, без кнопок технического ACK/resolve.

После commit выполняется немедленная попытка. Существующий notification scheduler
также обрабатывает очередь Incident. Всего допускается пять попыток; задержки
перед оставшимися попытками — 30, 60, 120 и 240 секунд, с учётом периода scheduler.
Захват доставки истекает через 300 секунд, позволяя восстановить работу после
остановки обработчика.

Уникальный ключ события/канала/адресата предотвращает дубли очереди. Успешные
каналы и push-подписки сохраняются при повторе, поэтому ошибка другого адресата
обычно не вызывает повторной доставки уже успешным. Неактуальные запросы и
неактивные подписки могут пропускаться; исчерпавшие попытки получают статус failed.

Гарантия — **at least once**: при сбое после принятия провайдером, но до сохранения
успеха возможен дубль. Успешный HTTP-ответ не гарантирует доставку. Scheduler должен
работать; при диагностике проверяйте failed-записи `incident_notification_delivery`
и логи, не раскрывая credentials провайдера и push endpoints.
