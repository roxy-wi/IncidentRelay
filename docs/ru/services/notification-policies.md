# Политики уведомлений

Политики уведомлений определяют, какие общие каналы уведомлений получают события
для сервиса.

Они полезны, когда несколько маршрутов относятся к одному логическому сервису и
должны использовать одинаковые правила уведомлений. Вместо копирования списков каналов в
каждый маршрут назначьте сервису одну политику уведомлений и настройте
маршрут на её использование.

## Как работают политики уведомлений

Политика уведомлений принадлежит одной команде и содержит упорядоченные правила.

Каждое правило определяет:

- типы событий, которые оно обрабатывает;
- необязательные матчеры алертов;
- один или несколько каналов уведомлений;
- продолжается ли вычисление после срабатывания правила;
- включено ли правило.

Правила вычисляются по позиции, начиная с наименьшей позиции.

Когда правило срабатывает, его каналы добавляются к целям доставки. Затем вычисление
останавливается, если для этого правила не включён параметр **Continue matching**.

Дублирующиеся каналы удаляются перед доставкой.

## Типы событий

Правило может обрабатывать один или несколько типов событий:

| Тип события    | Описание                                      |
|----------------|-----------------------------------------------|
| `notification` | Первичные уведомления об алертах и обновления алертов |
| `reminder`     | Напоминания о неподтверждённых алертах        |
| `escalation`   | Уведомления об эскалации                       |

События подтверждения и разрешения не выбирают каналы повторно. IncidentRelay
обновляет сообщения, созданные предыдущими доставками.

Это означает, что изменение или удаление политики уведомлений не мешает
IncidentRelay обновить уже доставленное сообщение при подтверждении или разрешении
алерта.

## Матчеры

Правила политики уведомлений используют тот же формат матчеров, что и правила сопоставления сервисов.

Общий редактор может предлагать имена и значения меток из недавних алертов команды. См. [Матчеры алертов](../concepts/matchers.md).

Пустой объект матчера соответствует любому алерту:

```json
{}
```

Сопоставление по серьёзности:

```json
{
  "severity": "critical"
}
```

Сопоставление по приоритету:

```json
{
  "priority": ["p1", "p2"]
}
```

Сопоставление по меткам:

```json
{
  "labels": {
    "environment": "production",
    "namespace": {
      "regex": "^payments-"
    }
  }
}
```

Сопоставление по полям сервиса или команды:

```json
{
  "fields": {
    "service.slug": "payments-api",
    "team.slug": "platform"
  }
}
```

Правило-перехватчик (catch-all) обычно размещается последним, чтобы алерты, не обработанные более ранними
правилами, всё же получали уведомление.

## Режимы каналов маршрута

Маршрут управляет тем, как IncidentRelay комбинирует собственные каналы с сопоставленной
политикой уведомлений сервиса.

| Режим                       | Поведение                                                     |
|-----------------------------|---------------------------------------------------------------|
| `route_only`                | Использовать только каналы, настроенные непосредственно на маршруте |
| `service_policy`            | Использовать только каналы, выбранные политикой уведомлений сервиса |
| `service_policy_plus_route` | Комбинировать каналы политики сервиса и каналы маршрута        |

Существующие маршруты по умолчанию используют `route_only`, поэтому включение политик уведомлений не
изменяет их текущее поведение доставки.

### Отсутствие неявного отката

`service_policy` не откатывается к каналам маршрута.

Если у сопоставленного сервиса нет политики, политика отключена или ни одно включённое правило
не соответствует событию, этот режим маршрута не выбирает общий канал.

Используйте `service_policy_plus_route`, когда каналы маршрута должны оставаться запасным вариантом или
всегда должны получать событие.

Персональные правила уведомлений, включая правила браузерных push-уведомлений, вычисляются
отдельно от политик общих каналов.

## Настройка политики уведомлений

1. Откройте **Services → Notification Policies**.
2. Выберите **New policy**.
3. Выберите команду-владельца.
4. Введите имя и необязательное описание.
5. Сохраните политику.
6. Откройте меню действий политики и выберите **Rules**.
7. Добавьте правила в нужном порядке вычисления.
8. Выберите типы событий, матчеры и каналы для каждого правила.
9. Сохраните каждое правило.

Включённое правило должно содержать хотя бы один канал уведомлений. Отключённое правило
можно сохранить без каналов.

## Назначение политики сервису

1. Откройте **Services → Service Catalog**.
2. Создайте или отредактируйте сервис.
3. Выберите значение в поле **Notification policy**.
4. Сохраните сервис.

Сервис может использовать только включённую политику уведомлений, принадлежащую той же команде.

Политику, назначенную сервису, нельзя удалить. Удалите политику из всех
сервисов, прежде чем удалять её.

## Настройка маршрута

1. Откройте **Routes**.
2. Создайте или отредактируйте маршрут.
3. Выберите **Notification channel source**.
4. Выберите один из вариантов:
   - **Route channels only**;
   - **Service notification policy**;
   - **Service policy + route channels**.
5. Сохраните маршрут.

Для режимов политики сервиса у группы алертов должен быть сервис. Сервис может
поступать из сервиса маршрута по умолчанию или из совпадающего правила сервиса.

## Пример: критические алерты и правило-перехватчик

Правила политики:

1. **Critical alerts**
   - типы событий: `notification`, `reminder`, `escalation`;
   - матчер: `{"severity": "critical"}`;
   - каналы: Mattermost и Telegram;
   - continue matching: отключено.

2. **Default alerts**
   - типы событий: `notification`;
   - матчер: `{}`;
   - каналы: Email;
   - continue matching: отключено.

Критический алерт использует Mattermost и Telegram и останавливается на первом правиле.
Некритический первичный алерт пропускает первое правило и использует Email.

## Пример: комбинирование нескольких совпадающих правил

Правила политики:

1. **Production alerts**
   - матчер: `{"labels": {"environment": "production"}}`;
   - каналы: Operations Mattermost;
   - continue matching: включено.

2. **Critical alerts**
   - матчер: `{"severity": "critical"}`;
   - каналы: Emergency Telegram;
   - continue matching: отключено.

Критический production-алерт получает доставку и через Mattermost, и через Telegram.
Некритический production-алерт получает доставку только через Mattermost.

## Отключённые ресурсы

IncidentRelay игнорирует:

- отключённые политики;
- отключённые правила;
- отключённые или удалённые каналы.

Правило политики, которое не включает текущий тип события, пропускается.

## Рекомендуемая настройка

- Держите правило-перехватчик последним, когда каждое событие должно достигать общего канала.
- Используйте специфичные правила перед общими.
- Используйте `continue_matching` только тогда, когда каналы из нескольких правил должны
  комбинироваться.
- Используйте `service_policy`, когда политика сервиса является авторитетной конфигурацией
  доставки.
- Используйте `service_policy_plus_route`, когда каналы уровня маршрута также должны получать
  события.
- Тестируйте правила напоминаний и эскалаций отдельно от правил первичных уведомлений.
