# Токены приёма маршрута

Входящие интеграции аутентифицируются с помощью токенов приёма маршрута.

Токен принадлежит маршруту, а не каналу.

```text
Monitoring system -> Integration endpoint -> Route token -> Route -> Service -> Channels
```

## Почему токены принадлежат маршрутам

Маршрут определяет:

- тип источника, такой как `alertmanager`, `zabbix` или `webhook`;
- команду;
- ротацию;
- необязательный сервис по умолчанию;
- матчеры;
- правила сопоставления сервисов через метки, аннотации алертов или поля полезной нагрузки;
- привязанные каналы уведомлений;
- поведение группировки.

Токен определяет, какой маршрут должен получать входящие алерты.

Каналы только описывают, куда доставляются уведомления.

## Назначение сервиса

После того как маршрут выбран, IncidentRelay может привязать алерт к сервису.

Используйте сервис по умолчанию маршрута, когда все алерты через маршрут принадлежат одной логической системе.

Используйте правила сопоставления сервисов, когда один маршрут получает алерты для нескольких логических систем.

Пример:

```text
Route: alertmanager-prod
Service rule 1: labels.job = RabbitMQ   -> RabbitMQ Cloud
Service rule 2: labels.job = PostgreSQL -> PostgreSQL Prod
Service rule 3: labels.app = billing    -> Billing API
```

## Использование

Используйте токен во входящем запросе интеграции, например:

```text
Authorization: Bearer ROUTE_TOKEN
```

Не помещайте токены маршрута в конфигурацию канала уведомлений.

## Перегенерация

Если токен маршрута потерян или скомпрометирован, перегенерируйте его на странице Routes и обновите конфигурацию системы мониторинга.

После перегенерации старый токен должен перестать работать.
